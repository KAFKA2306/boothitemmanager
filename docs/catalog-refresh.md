# Catalogue refresh

The published site is static, so freshness is implemented as bounded observation, material-diff detection, validation, and deployment rather than a server-side push channel.

## Schedule

`.github/workflows/catalog-refresh.yml` runs at minutes `7,22,37,52` of every hour and can also be started with `workflow_dispatch`. GitHub documents that scheduled workflows can be delayed under load and that the shortest supported interval is five minutes; avoiding minute `0` reduces the documented top-of-hour delay risk.

## Bounded source access

Each run:

1. checks the public BOOTH `VRChat` search page for newly listed item URLs;
2. selects at most 120 known items using a deterministic SHA-256 partition of the current catalogue;
3. fetches at most 30 newly discovered items in addition to that known-item slice;
4. waits between requests and honors HTTP retry/backoff behavior;
5. never deletes the last known good record after a fetch failure.

At the current catalogue size, 120 known items every 15 minutes gives a complete known-item rotation in about 84 hours. The partition depends only on the time slot and stable item IDs, so ephemeral CI runners do not need a mutable cursor.

## Material changes only

A successful observation changes tracked files only when seller-observed fields materially differ or an item first becomes unavailable. Unchanged observations stay in the per-run Actions evidence instead of rewriting catalogue timestamps, which keeps a no-op run free of commits and deployments. `api/freshness.json.last_catalog_change_at` therefore means the last material catalogue change, not the last network check. The public UI obtains the latest successful bounded observation time from the public GitHub Actions workflow API and falls back to the static change timestamp if that API is unavailable.

New items are inserted conservatively as `ASSET` with empty compatibility and tag fields until later evidence-based normalization. The refresh job does not invent avatar support, category, seller identity, or tags from weak signals.

## Validation and publication

Before any commit, the refresh workflow runs unit tests and `scripts/audit_static_api.py`. Only a validated material diff is committed to `main`. That push then uses the existing Pages workflow to build and deploy the exact same static artifact to GitHub Pages and Cloudflare Pages.

`dist/proof.json` is generated by `scripts/build_proof.py`. It separates build time from catalogue/source freshness and counts records from the actual shards instead of using a hard-coded item count.

## Failure behavior

Transient source errors are recorded in `build/refresh-report.json` and the workflow artifact. Discovery failure or more than 20% selected-item fetch failure fails the run before audit/commit; existing catalogue records are preserved. `src/boothitemmanager2/crawler.py` also uses a finite cache TTL and last-known-good fallback for local or bulk workflows, so a cached HTML file is no longer trusted indefinitely.

## Upstream contracts and platform limits

- BOOTH Guidelines: https://booth.pm/guidelines
- GitHub Actions `schedule`: https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule
- GitHub Actions concurrency: https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency

GitHub documents that scheduled workflows in public repositories are automatically disabled after 60 days without repository activity. This repository therefore keeps `workflow_dispatch` as a recovery path; the refresh implementation itself does not manufacture no-op commits merely to keep a scheduler alive. If the repository ever becomes intentionally inactive for that long, re-enabling the workflow is a platform operation rather than a catalogue-data change.
